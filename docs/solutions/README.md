# docs/solutions

이번 작업에서 겪은 문제와 그 해결책 중, **다음 작업에서도 재사용할 가치가 있는 것**만
골라 기록하는 곳이다. 단순 회고록이 아니라, AI(그리고 사람)가 다음 작업을 시작하기
전에 참고하는 "프로젝트 기억"이다.

## 기록 기준

아래에 해당할 때만 기록한다. 해당하지 않으면 기록하지 않는다.

- 같은 실수나 논의가 두 번 이상 반복됐다
- 코드 리뷰에서 나온 지적이 이 프로젝트에 일반적으로 적용된다
- 새로운 프로젝트 규칙/컨벤션이 확정됐다
- 다음 기능에서도 재사용 가능한 해결책을 찾았다
- AI가 맥락 없이는 자주 놓치는 부분을 발견했다

한 번만 있었던 사소한 실수, 이 프로젝트에서만 통하는 임시방편은 기록 대상이 아니다.

## 카테고리

- `concurrency-issues/` — 동시성 제어(락, 트랜잭션 격리 수준, 재고 차감 경쟁 조건 등)
- `idempotency-issues/` — 멱등성 처리(중복 웹훅, 재시도로 인한 중복 실행 등)
- `integration-issues/` — 외부 연동(OTA 웹훅/API 시뮬레이션, 재시도·타임아웃 등)
- `database-issues/` — 스키마, 마이그레이션, 쿼리 성능, 락 관련 DB 이슈
- `architecture-patterns/` — 모듈 구조, 계층 분리, 이벤트/메시징 설계 판단
- `conventions/` — 코드 스타일, 네이밍, 패키지 구조 등 반복되는 관례
- `best-practices/` — 위 카테고리에 딱 들어맞지 않는 일반적인 권장 사항

새 카테고리가 필요하면 이 목록에 먼저 추가하고 폴더를 만든다.

## 기록 방법

1. 각 카테고리 폴더 안에 `YYYY-MM-DD-짧은-제목.md` 형식으로 파일을 만든다.
2. [TEMPLATE.md](./TEMPLATE.md) 형식을 따른다.
3. 반복되는 규칙으로 굳어졌다면 이 폴더에 남기는 것과 별개로, 프로젝트 루트의
   [CLAUDE.md](../../CLAUDE.md)에도 규칙으로 반영할지 검토한다.

## 다음 작업 시작 전 참고 방법

새 기능을 시작하기 전, 관련 카테고리 폴더를 먼저 훑어보고 이미 정리된 판단이나
함정이 없는지 확인한다. 예: "`concurrency-issues/`와 `idempotency-issues/`를 참고해서
이번 기능의 동시성 처리 방안을 세워줘."
